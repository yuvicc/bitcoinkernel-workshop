01
Part one

Bitcoinkernel

What it is, why it exists, and what it needs from you.

Part one: the why and the what. About 25 minutes.

The problem

Bitcoin Core is a monolith

Validation logic lives inside the same process, and often the same code paths, as networking, mempool, wallet, RPC and GUI.

To validate blocks exactly like Bitcoin Core, you had to run all of Bitcoin Core.

Historically Core grew as one program. Validation code reached into global state, command-line args, the GUI's interfaces and more.

If you wanted Core's exact rules in your own software, the options were: run bitcoind and talk RPC, or reimplement the rules yourself. Both have costs.

Why it matters

Consensus is defined by code, bugs included

Every node must agree on validity for every block, forever. A disagreement is a chain split.

Consensus isn't the spec in someone's head. It's what the deployed code actually does, edge cases and all.

2013

Core vs Core

v0.8 switched to LevelDB and accepted a block that v0.7's BerkeleyDB lock limits couldn't. The result was an accidental chain split. Even the database was consensus.

2022

Reimplementations drift

btcd, and LND on top of it, twice rejected valid blocks with large Taproot witnesses and stalled on a stale tip.

Two stories. In March 2013, Bitcoin Core 0.8 vs 0.7: same project, different database, and the network split for several hours. Rule-for-rule equivalence isn't enough; you need bug-for-bug equivalence.

In October and November 2022, btcd had wire-level witness size limits that Core didn't have. Blocks containing big Taproot witnesses were rejected, and LND nodes using btcd as backend stopped following the chain.

Takeaway: if you want Core's consensus, use Core's code.

Previous attempt

libbitcoinconsensus

A shared library exposing one function: verify a single script.

  • No block validation
  • No chainstate or UTXO set
  • Script is a small slice of consensus
  • Little adoption. Deprecated in v27, removed in v28 (#29189)
LessonA useful consensus library has to own state: blocks, UTXOs, the chain.

libbitcoinconsensus existed for years. It was stateless and tiny, so it couldn't tell you whether a block is valid; that needs the UTXO set, the chain, and contextual checks.

It saw little adoption and was removed in v28. The kernel is the "do it properly" successor.

Enter

libbitcoinkernel

"A stateful library that can spawn threads, do caching, do I/O"Bitcoin Kernel Library Project Tracking, bitcoin/bitcoin#27587

The same code

It's the validation engine that Bitcoin Core itself runs, not a reimplementation.

A C API

A single header, bitcoinkernel.h, with opaque btck_* handles and functions.

Incremental

Core is refactored step by step until its own node code becomes a consumer of the kernel.

Key word: stateful. This is not a pure function library. It manages a data directory, LevelDB databases, block files, a thread pool for script checks, and caches.

And it's the same code Core runs, extracted rather than rewritten.

Scope

What's in and what's out

In the kernel

  • Block & header validation
  • Script verification (P2SH, SegWit, Taproot)
  • Chainstate: the UTXO set in LevelDB
  • Block storage: blk*.dat, rev*.dat, block index
  • Reading blocks and undo data
  • Validation notifications & callbacks

Left to you

  • P2P networking & peer management
  • JSON-RPC, REST, ZMQ servers
  • Wallet
  • Mempool & relay policy (for now)
  • Additional indexes (txindex, filters…)
  • User interface

The kernel decides what is valid and remembers what the chain is. Everything about how you get data and how you present it is yours.

That's the opportunity: bring your own P2P stack (or none at all, as in our exercises), your own indexes, your own UI.

Architecture

Where it sits

Your app feeds bytes in: blocks, headers, transactions. The kernel validates them, persists them in a Core-compatible data directory, and calls you back with events.

The on-disk layout is the same as bitcoind's, which is why tools can read an existing Core datadir (with bitcoind stopped!).

Design

Why a C API over a C++ core?

01

Universal FFI

Every language can call C: Rust extern "C", Python ctypes/cffi, Go cgo, Java FFM, C# P/Invoke, Swift, Zig…

02

ABI stability

C++ name mangling, templates, exceptions and STL layouts don't cross compiler or language boundaries. C does.

03

Freedom to refactor

A narrow, opaque surface lets Core rework its internals without breaking downstream users.

For C++ users there is also a header-only RAII wrapper, bitcoinkernel_wrapper.h (btck:: namespace), on top of the C API.

The implementation is C++, but the interface is C. That's deliberate: C is the lingua franca for FFI.

The C++ wrapper gives you RAII handles, ranges and virtual classes for notifications. My C++ node uses it; you'll see it later.

Design

The C API in one slide

  • Opaque handles: btck_Context*, btck_Block*, … You never see the struct.
  • Every *_create pairs with a *_destroy.
  • const return values are views, borrowed from their parent. Don't destroy them.
  • Blocks and transactions are refcounted: *_copy is cheap.
  • Callbacks take a void* user_data. This is where bindings hook in closures.

You won't write C today; the Rust crate does all of this for you. But knowing the shape helps you understand the Rust API: every Rust type wraps one of these handles, and Drop calls the matching destroy.

"Views" become Rust's XRef<'a> types with lifetimes, so the borrow checker enforces what the C docs only ask for politely.

Capabilities

Three ways to use the kernel

Context-free validation

Verify a script or check a block's structure, PoW and merkle root. No disk, no chainstate.

verify() · Block::check()*

Full validation

Feed blocks and headers to a ChainstateManager. The kernel validates, stores and connects them to the best chain.

process_block() · process_block_header()

Data access

Walk the block index and read blocks plus undo data (spent outputs) from any Core datadir.

read_block_data() · read_spent_outputs()

* Block::check is on rust-bitcoinkernel master, not yet in the 0.2.1 release.

These three modes cover almost every use case. The exercises today touch all three: exercise 2 is full validation, exercise 3 is data access, and exercise 4 is context-free script verification.

The build requirements are Bitcoin Core's own. Bindings like rust-bitcoinkernel vendor Core and build it with CMake behind the scenes, so you need the toolchain even though you "only" add a crate.

The datadir is exclusive: two processes opening the same LevelDB will fail or worse. Copy the datadir, or stop bitcoind.

Most important: the API is not stable. That's also an invitation. Issue #31878 collects feedback from people using the kernel in alternative implementations.

Mental model

The object graph

Everything hangs off a Context. The ChainstateManager owns a data directory. From it you get the active Chain, entries in the block tree, and from those, blocks and their transactions.

Things you get out of a parent are usually borrowed views (…Ref<'a>). The lifetime ties them to their parent, so you can't use a transaction after its block is dropped. Call to_owned() if you need to keep it.

Most accessor methods live on extension traits, so always import the prelude.

Context

Building a Context

  • Selects the chain: Mainnet, Testnet, Testnet4, Signet, Regtest
  • Registers notifications, the kernel telling you what happened
  • Closures must be Send + Sync + 'static
  • Context is Send + Sync. Share it via Arc
  • context.interrupt() stops long operations

The builder is the entry point. Chain type determines genesis, consensus params and checkpoints.

Notifications available: block_tip, header_tip, progress, warning_set, warning_unset, flush_error, fatal_error.

On fatal_error the kernel is in an unrecoverable state. Tear everything down.

Callbacks

The validation interface

block_checkedVerdict for a block, valid or not, with a reason
new_pow_valid_blockA block with valid PoW extends the tip
block_connectedBlock joined the active chain
block_disconnectedBlock left it (reorg)
Callbacks run on the kernel's own thread. Keep them short and send work elsewhere with a channel.

Notifications are about progress. The validation interface is about verdicts and chain changes.

block_checked is where you learn why a block was rejected: state.result() gives a BlockValidationResult such as Consensus, Mutated, MissingPrev, TimeFuture…

Gotcha: for new_pow_valid_block the closure takes (entry, block), entry first. The others take (block, entry).

Observability

Logging

  • Implement the Log trait and hand it to Logger::new
  • Keep the Logger alive. Dropping it disconnects the log callback
  • Categories: Validation, BlockStorage, CoinDb, LevelDb, Kernel, …
  • Levels: Trace, Debug, Info
  • Settings are global and affect every Logger

A classic Rust footgun: let _ = Logger::new(..) drops immediately. Use a named binding like _logger or logger.

Messages emitted before a logger exists are buffered (up to about 1 MB) and flushed once you connect one.

State

ChainstateManager

worker_threads(n)Parallel script checks, clamped to 0–15
wipe_db(bt, cs)Reindex knobs. (true, false) is invalid
*_db_in_memoryGreat for tests. Mainnet UTXO set is GBs
import_blocks()Runs the reindex / loads existing block files
After any wipe_db, call import_blocks() before anything else.

data_dir holds the chainstate; blocks_dir holds blk/rev files. Both are created if missing. Note the block index DB always lives under data_dir/blocks/index regardless of blocks_dir.

wipe_db(false, true) rebuilds only the chainstate from the block files you already have. (true, true) is a full reindex.

Dropping the ChainstateManager flushes state to disk. More on shutdown order later.

Full validation

Feeding blocks: process_block

CarefulNewBlock means "written to disk". It does not mean valid, and it does not mean on the active chain.
  • Validity: the block_checked callback
  • Chain membership: block_connected, or active_chain().contains(&entry)
  • Blocks may arrive out of order. The kernel connects them once parents are known
  • Headers first? process_block_header(&header)

This is the #1 misunderstanding. process_block tells you what happened to storage. The verdict comes through the validation interface.

My C++ node has a comment on exactly this: "ProcessBlock succeeding only means processing ran; the verdict lands in the validation interface."

No P2P, no RPC: just bytes into the engine. These blocks get the full treatment: PoW, merkle root, coinbase rules, and script checks once there are real spends.

The bonus is fun: corrupting a transaction byte gives a merkle mismatch, reported as Mutated.

Data access

Walking the chain

  • active_chain() is a live view. Re-query after processing
  • iter() goes genesis → tip
  • prev() and ancestor(h) walk backwards. There is no next(), so use at_height(h + 1)
  • BlockTreeEntry has no PartialEq. Compare block_hash()
  • best_entry() is the most-work header, which may be ahead of the tip

BlockTreeEntry wraps Core's CBlockIndex: height, hash, header, pointer to parent. It's cheap and Copy.

The lifetime 'a ties entries to the ChainstateManager, so you can't keep them after dropping it.

Data access

Blocks and undo data

Undo data (rev*.dat) stores every coin a block spent: value, script, height and coinbase flag.

Off by oneUndo data skips the coinbase: spent[i] belongs to tx[i + 1].

Inputs expose only the outpoint and sequence. For scriptSig or witness, re-parse the tx with rust-bitcoin.

Undo data is what makes the kernel great for indexers: for every input you get the previous output without a txindex or a UTXO lookup.

That .skip(1) is the most common bug I see. Coinbase inputs spend nothing, so undo has no entry for them.

Context-free validation

Script verification

VERIFY_P2SHBIP16
VERIFY_DERSIGBIP66 strict DER
VERIFY_NULLDUMMYBIP147
VERIFY_CHECKLOCKTIMEVERIFYBIP65
VERIFY_CHECKSEQUENCEVERIFYBIP112
VERIFY_WITNESSBIP141/143
VERIFY_TAPROOTBIP341/342

None means VERIFY_ALL. Taproot needs every spent output in the precomputed data.

This is the libbitcoinconsensus use case, done properly. You need the spent output's scriptPubKey and amount, the spending tx, and the input index.

PrecomputedTransactionData caches sighash midstates. For Taproot you must pass all spent outputs because BIP341 signatures commit to all of them.

On master the flags become a typed ScriptVerificationFlags. Another reason to pin versions.

Exercise 4

Verify Satoshi's signature yourself

Tasks · src/bin/ex4_verify.rs

  1. Read block 170 and its undo data from your chainstate
  2. Take transaction #1 (Satoshi → Hal) and its spent coin
  3. Build PrecomputedTransactionData and call verify on input 0
  4. Tamper: change an output value in the raw tx and verify again
cargo run --bin ex4_verify
⏱ 10 min
ExpectOriginal: Ok(()). Tampered: Err(ScriptVerify(Invalid)).

Your code just checked an ECDSA signature Satoshi made on 12 Jan 2009. You trusted no one.

The spent output is a P2PK script: Satoshi's pubkey followed by OP_CHECKSIG. The scriptSig is just the signature.

Changing any output changes the sighash, so the signature no longer matches. That's the whole security model in one error.

Things to keep in mind · 1/2

Lifecycle & threads

Never panic in a callback

Callbacks are called from C++. A panic unwinds across extern "C". Catch errors and send them over a channel.

Callbacks run on kernel threads

They must be Send + Sync + 'static. Use Arc, atomics and channels. Don't block for long.

Shutdown order

Drop the ChainstateManager (it flushes to disk), then the Context. Keep the Logger alive until the end.

Exclusive datadir

Stop bitcoind or copy its datadir first. Two processes on the same LevelDB will not end well.

Fatal means fatal

On fatal_error or flush_error, tear down the context and chainstate manager. Don't try to continue.

Chain isn't Send

ChainstateManager is Send + Sync, but the Chain view is not. Re-fetch it on each thread.

These are the things that bite people in real projects, not in toy examples.

Panic across FFI is undefined behaviour or an abort depending on the Rust version. Wrap callback bodies defensively.

Things to keep in mind · 2/2

Data & API

Unstable API

Pin bitcoinkernel = "=x.y.z". Signatures change between releases, e.g. verify flags from u32 to a typed struct.

Stored ≠ valid

ProcessBlockResult::NewBlock is about storage. Use block_checked for the verdict.

Undo skips coinbase

spent_outputs[i] ↔ transactions[i + 1].

Reindex rules

wipe_db(true, false) is invalid. After any wipe, call import_blocks() first.

Limited tx accessors

No scriptSig or witness getters yet. Pair with rust-bitcoin via consensus_encode().

Fixed cache

DB cache size isn't configurable from Rust (0.2.1). In-memory chainstate means the whole UTXO set in RAM.

If you remember one thing: pin your versions and read the changelog. The API is still moving, which is also why your feedback matters.

Rust · Utreexo

Floresta & Utreexo

rust-bitcoinkernel
github.com/getfloresta/Floresta

Utreexo

Replace the multi-GB UTXO set with a hash-based accumulator: a forest of Merkle roots that fits in about a kilobyte. Inclusion proofs travel with blocks and transactions.

Tadge Dryja, MIT DCI, 2019

Floresta

A lightweight, embeddable Utreexo-powered full node in Rust, with an integrated Electrum server.

"Instead of reimplementing a Bitcoin Script interpreter, we use rust-bitcoinkernel…"

Why #35187 matters

btck_chainstate_manager_validate_block takes a callback that supplies the spent coins, so the caller provides the UTXOs. That's exactly the Utreexo model.

Open PR by sedited

Utreexo nodes don't keep a UTXO database. They keep accumulator roots and verify proofs that the spent outputs exist.

Floresta already delegates script validation to the kernel via rust-bitcoinkernel, which makes it bug-compatible with Core where it matters most.

Today the kernel's full block validation assumes it owns the UTXO set. PR #35187 adds a path where you supply the coins a block spends via a callback. It runs CheckBlock, contextual checks and ConnectBlock against those coins. That's the missing piece for Utreexo, and also useful for SwiftSync-style designs.
